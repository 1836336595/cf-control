# Cable-length geometry and calibration acceptance audit

This note distinguishes the configured **effective geometry** from a physical tape measurement. The controller computes each distance as

```text
d_i = || p_payload + R_payload rho_i - p_vehicle_i ||
```

where `rho_i` is the configured payload attachment point and `p_vehicle_i` is the measured Crazyflie rigid-body center. This is implemented in [`slung_load_controller.py:609`](../../slung_load_controller.py#L609). The user confirmed those modeled points correspond to the physical endpoints being measured. Thus the distance is directly relevant to this cable geometry, while differences can still reflect attachment-point calibration, rigid-body mocap calibration, or rope-length changes; it is not a direct tape measurement of rope material length.

The per-vehicle effective lengths enter different parts of the controller in different ways:

- TAKEUP target distance is `d_target = L_effective - slack`; see [`slung_load_controller.py:445`](../../slung_load_controller.py#L445). `takeup_vehicle_targets()` places the aircraft relative to the payload attachment and target distance, adding the configured outward margin while preserving the requested geometric distance where possible ([`slung_load_controller.py:534`](../../slung_load_controller.py#L534)). The handoff check compares measured distance against both this target and the effective-length bound ([`slung_load_controller.py:461`](../../slung_load_controller.py#L461), [`ctbr_controller.py:3804`](../../ctbr_controller.py#L3804), [`ctbr_controller.py:4026`](../../ctbr_controller.py#L4026)).
- The static 6x9 force/moment allocation matrix depends on payload attachment vectors `rho`, not cable lengths ([`slung_load_controller.py:734`](../../slung_load_controller.py#L734), [`slung_load_controller.py:776`](../../slung_load_controller.py#L776)). The allocated signed tension follows the measured link direction `q` and allocated force `mu_id` ([`slung_load_controller.py:925`](../../slung_load_controller.py#L925)).
- Measured cable direction and rate are reconstructed from attachment-to-aircraft geometry. In the kinematic feedforward, `L_effective` multiplies the centripetal term `m L |omega_link|^2 q`, while the angular-acceleration term `m q (q·a_i)` has **no** length factor ([`slung_load_controller.py:948`](../../slung_load_controller.py#L948)). The lateral link correction is `m L cross(q, correction)` and therefore scales linearly with effective length ([`slung_load_controller.py:954`](../../slung_load_controller.py#L954)). These are the direct force-model effects of an effective-length error; cable geometry mismatch also changes the measured vehicle/link states and thus `q`/`qdot` indirectly.

For the 2026-10-18 16:24:55 run, the configured vector was `[0.689, 0.699, 0.664] m`. The CSV's `link_length_measured_m` field is updated only on eligible calibration samples, so it is a **frozen last eligible geometry sample**, not a continuous live reading. It reported approximately `[0.71811, 0.70275, 0.68464] m` in the loaded phase: deltas `[+29.11, +3.75, +20.64] mm` from configured lengths. Stable windows did exist: each vehicle had 610 CSV rows with `within_tolerance`, a median window of 3.001 s, a maximum of 3.030 s, and up to 211 samples. The effective vector stayed nominal because those windows ended with `no_positive_mismatch`, not because the window failed stability or sample-count requirements.

There is a strict acceptance-bound contradiction in the current YAML. `takeup_distance_tolerance_m` is `0.030 m`, and `link_calibration_max_adjustment_m` is also `0.030 m` ([`slung_payload.yaml:114`](../../../config/slung_payload.yaml#L114), [`slung_payload.yaml:82`](../../../config/slung_payload.yaml#L82)). The calibrator applies only when some positive estimate is **strictly greater than** the mismatch tolerance ([`slung_link_calibration.py:137`](../../slung_link_calibration.py#L137)), but rejects any estimate **greater than** the maximum adjustment ([`slung_link_calibration.py:134`](../../slung_link_calibration.py#L134)). With equal limits, no stable candidate can satisfy both checks: a delta at or below 30 mm is `within_tolerance`; any delta above 30 mm is `out_of_bounds`. I verified this directly with the current helper and matching limits. Thus the current configuration can collect a stable window but can never apply a positive calibration. Any new limits should be based on separately validated endpoint geometry and preserve the existing measured-distance, clearance, and pair-safety gates.

For an independent-length simulation, vary the MuJoCo physical tendon lengths while holding the controller's nominal lengths fixed. Test matched and asymmetric errors separately and log each physical tendon length, controller effective length, endpoint-to-center distance, Takeup target distance, measured direction error, and allocated signed tension. This separates the physical rope constraint from the controller's geometric estimate without treating either as a tape measurement.
